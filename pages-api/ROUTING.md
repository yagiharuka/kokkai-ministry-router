# 判定処理（2026-10-10、公開版37）

質問ごとに実際の国会質疑を探し、自然言語の文脈で関連性を確認してから、答弁者の肩書きから読んだ所属を集計する。政策名ごとの省庁辞書は使わない。

1. 質問全文から中心となる名詞句を抽出し、AIの検索語生成を待たずに発言検索を開始する。「どのような」「行っているか」などの文法語や一般的な「分野」を検索語につなげない。まず中心の2概念を検索し、薄いときは中心対象の短い語でも探す。2001年以降を対象に、APIが返す最新100発言の本文を再利用する。固有の事業名について、直近3年に発言がないだけで候補なしにしない。
2. 発言番号が連続する範囲で議員質問から次の議員質問までの政府答弁を対応させる。欠番をまたいで答弁を結び付けない。委員長の手続発言を除く。
3. 検索の関連度が比較的高い異なる12質疑・3会議以上が既に対応づけられれば、全文の追加取得を省く。それ未満なら、発言検索で観測した会議名と日付範囲を使い、最大10会議を1要求で補う。少数の候補が見つかっただけで検索を終了せず、要求の上限内で短い対象語による追加検索を行う。会議単位APIの出力順は全体の新しさ順ではないため、日付と実際に観測した委員会で範囲を絞る。直接取得のNDL要求は最大3回。AIによる言い換えは別の取得ラウンドとして上限3回。
4. 質問と答弁それぞれの検索上の関連度を使って候補を並べ、会議の分散も考慮する。多論点の質問の一部が一致するだけで、無関係な後続答弁の優先度を一律に上げない。同一質疑・同一所属の反復で枠を埋めず、同一質疑の別省庁の答弁も保持する。最大24の質疑・所属の組合せを文脈判定する。同じ所属の複数答弁はひとまとめで判定し、後の答弁を選べるよう原文番号とURLの対応を保つ。検索上の関連度は採用条件ではなく、採否は質問全文を使った文脈判定で決める。
5. 通常は最大8候補ずつ3並列で文脈を確認する。モデルは短い採否理由、候補ID、原文に付けた質問・答弁の番号を返す。引用文、所属、URL、割合を生成させない。番号は候補内の原文辞書と厳密に照合し、選ばれた答弁の元URL・肩書き・本文をそのまま使用する。未知の番号は判断保留。欠落・重複・不正な候補IDは、その候補だけ判断保留にし、原文で確認できた他の候補は残す。未知IDの行は受け付けない。判定バッチ全体が壊れた場合にも他のバッチの正常な判定は残す。
6. 対象・制度・活動領域・求める措置・国内外の範囲を文脈で確認する。単語の一致数を採用条件にしない。広い推進の問いには同じ活動の障壁除去や環境整備も認める。固有制度を具体的に説明する答弁は、元の質問が広い政策課題でも採用可能。外国だけの事例、別分野の一般論、別の問いへの答弁、決議の読み上げと挨拶は除く。
7. 同一質疑・同一省庁を一件とし、一質疑に複数省庁が答えた場合は重みを均等に分ける。割合は取得・採用した標本の内訳で、将来の担当確率ではない。兼務を解決できなければ省庁を推測しない。
8. 実際の質問・答弁の候補がゼロの場合だけ、AIで検索語を言い換えて再取得する。AIが空白区切りの代わりに生成した `AND` 演算子は除き、NDLに文字列 `AND` を検索させない。文脈判定の失敗を再試行・再分割の連鎖にせず、未判定候補として保つ。

## 応答と費用

GitHub Pagesの画面とCloudflare Workers AI bindingを使う。モデルは `@cf/openai/gpt-oss-20b` 固定、Workers Freeのみ。旧OpenAIキー、Qwen、有料サービスへの自動切替は使わない。

NDLの機械的アクセスは多重要求を避け、取得完了後3秒の間隔を維持する。高速化のためにこの間隔を短縮しない。公開会議録を条件の完全一致で1時間キャッシュし、Cloudflare Cache APIでも再利用する。同じ質問の判定はプロセス内10分キャッシュし、一部失敗のない完了結果はCache APIでも10分保存する。判定キャッシュのキーは質問全文・公開版・モデル・接続状態を含む条件のハッシュ。プロセス再起動後も同じ質問を再利用するが、別の質問や別の公開版へ前の判断を持ち越さない。同時に来た同じ質問はキャッシュ照合中も二重判定しない。

文脈判定の一要求は25秒でタイムアウトし、公開画面の待機を再試行で際限なく伸ばさない。原文の取得と文脈判定の所要時間を別々に記録する。法令検索は補助資料として非同期表示し、判定結果を待たせない。

公開画面は採用された質疑を最大24件表示する。短い原文抜粋を先に表示し、前後の質問・答弁は展開して読める。判断保留と判定済みの割合を分け、未判定の残り件数も表示する。

## 検証

`npm test` は、自然な質問文の検索語、AND表記、薄い標本での追加取得、発言の対応、所属、集計、引用の原文番号、24候補の選択、並列処理、後の答弁の選択、部分失敗、検索計画を待たない公開経路、プロセス再起動後の同一質問キャッシュと二重判定防止、表示と古い法令結果の混入防止を確認する。模擬モデル応答のテストは意味判定の精度測定ではない。

少数の原文付き確認例は開発用であり、独立した代表的な正答率評価ではない。取得件数・会議数・抜粋長に上限があり、候補に入らなかった答弁は判定できない。採用ゼロは会議録の不存在を意味しない。

旧形式の `reviewAssignments` とMCPの年別取得は互換用として残す。共通の発言対応・候補分散選択は `routing-core.mjs`、公開サイトの取得は `fast-retrieval.mjs`、公開サイトの判定は `reviewCompactAssignments` を使う。

仕様： [NDL API](https://kokkai.ndl.go.jp/api.html)、[Cloudflareモデル](https://developers.cloudflare.com/workers-ai/models/gpt-oss-20b/)、[Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/)。
