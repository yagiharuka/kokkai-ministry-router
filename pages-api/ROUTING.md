# 判定処理（2026-10-11、公開版44）

質問ごとに実際の国会質疑を探し、自然言語の文脈で関連性を確認してから、答弁者の肩書きから読んだ所属を集計する。政策名ごとの省庁辞書は使わない。

1. 質問全文から中心となる名詞句を抽出し、AIの検索語生成を待たずに発言検索を開始する。「どのような」「行っているか」などの文法語や一般的な「分野」を検索語につなげない。まず中心の2概念を検索し、薄いときは中心対象の短い語でも探す。2001年以降を対象に、APIが返す最新100発言の本文を再利用する。固有の事業名について、直近3年に発言がないだけで候補なしにしない。
2. 発言番号が連続する範囲で議員質問から次の議員質問までの政府答弁を対応させる。欠番をまたいで答弁を結び付けない。委員長の手続発言を除く。
3. 検索の関連度が比較的高い異なる12質疑・3会議以上が既に対応づけられれば、全文の追加取得を省く。それ未満なら、発言検索で観測した会議名と日付範囲を使い、最大10会議を1要求で補う。少数の候補が見つかっただけで検索を終了せず、要求の上限内で短い対象語による追加検索を行う。会議単位APIの出力順は全体の新しさ順ではないため、日付と実際に観測した委員会で範囲を絞る。直接取得のNDL要求は最大3回。AIによる言い換えは別の取得ラウンドとして上限3回。
4. 質問と答弁それぞれの検索上の関連度を使って候補を並べ、会議の分散も考慮する。多論点の質問の一部が一致するだけで、無関係な後続答弁の優先度を一律に上げない。同一質疑・同一所属の反復で枠を埋めず、同一質疑の別省庁の答弁も保持する。最大24の質疑・所属の組合せを文脈判定する。同じ所属の複数答弁はひとまとめで判定し、後の答弁を選べるよう原文番号とURLの対応を保つ。検索上の関連度は採用条件ではなく、採否は質問全文を使った文脈判定で決める。
5. 通常は最大8候補ずつ3並列で文脈を確認する。選択済みの24候補を保持し、同一の質問原文がある候補を同じバッチへ寄せる。質問原文の完全一致に限って同じバッチ内の候補IDで参照し、質問・答弁・前後文脈を削ったり要約したりしない。空の前後文脈とfalseの抜粋フラグは省略し、指示で既定値を明記する。モデルは `id, beneficiary, activity, relation, comparison, decision, q, a` を持つオブジェクトを `reviews` 配列で返す。対象と活動領域、受益者と提供者の役割を比較してから採否を決め、短い比較理由を表示する。広い支援・環境改善の問いには、同じ対象の障壁を除く具体策も採用できる。別分野の一般論、支援の提供者と受益者の取り違えは採用しない。文字数・全候補の完了・IDの重複・原文番号はサーバーで検証する。AI側のスキーマは項目名と型を指定し、実機でタイムアウトした複雑なスキーマを簡略化し、文字数制約を含めない（個別の制約が原因とは断定していない）。不採用・保留の原文番号は空にする。原文番号は160文字の固定幅ではなく文単位に付け、文中で対象者と取組を切断しない。引用文、所属、URL、割合を生成させない。番号は候補内の原文辞書と厳密に照合し、選ばれた答弁の元URL・肩書き・本文をそのまま使用する。未知の番号は判断保留。欠落・重複・不正な候補IDは、その候補だけ判断保留にし、原文で確認できた他の候補は残す。未知IDの行は受け付けない。判定バッチ全体が壊れた場合にも他のバッチの正常な判定は残す。出力上限による途中切れも診断情報に記録し、失敗した最大8候補は保留する。再試行・再分割を自動追加して消費を増やさない。
6. 対象・制度・活動領域・求める措置・国内外の範囲を文脈で確認する。施策の受益者と実施主体・規制対象を区別し、広い支援の問いには、同じ受益者・活動の障壁を除くための具体的なルールや環境整備も含める。会議名を判定に渡し、本会議の総花的な答弁を識別できるようにする。答弁の見出しだけの文は根拠番号の選択肢から除く。本会議の総理答弁が長くて質問・答弁を抜粋している場合、割り振りを確定できない文脈不足の候補として保持し、内訳に入れない。単語の一致数を採用条件にしない。広い推進の問いには同じ活動の障壁除去や環境整備も認める。固有制度を具体的に説明する答弁は、元の質問が広い政策課題でも採用可能。外国だけの事例、別分野の一般論、別の問いへの答弁、決議の読み上げと挨拶は除く。
7. 同一質疑・同一省庁を一件とし、一質疑に複数省庁が答えた場合は重みを均等に分ける。割合は取得・採用した標本の内訳で、将来の担当確率ではない。兼務を解決できなければ省庁を推測しない。
8. 実際の質問・答弁の候補がゼロの場合だけ、AIで検索語を言い換えて再取得する。AIが空白区切りの代わりに生成した `AND` 演算子は除き、NDLに文字列 `AND` を検索させない。文脈判定の失敗を再試行・再分割の連鎖にせず、未判定候補として保つ。

## 応答と費用

GitHub Pagesの画面とCloudflare Workers AI bindingを使う。モデルは `@cf/openai/gpt-oss-20b` 固定、Workers Freeのみ。旧OpenAIキー、Qwen、有料サービスへの自動切替は使わない。

NDLの機械的アクセスは多重要求を避け、取得完了後3秒の間隔を維持する。高速化のためにこの間隔を短縮しない。公開会議録を条件の完全一致で1時間キャッシュし、Cloudflare Cache APIでも再利用する。同じ質問の一部失敗のない完了結果はプロセス内とCache APIで最大24時間保存し、画面に元の検索日時を示す。未完了の結果の短期保存は30秒にとどめる。判定キャッシュのキーは質問全文・公開版・モデル・接続状態を含む条件のハッシュ。プロセス再起動後も同じ質問を再利用するが、別の質問や別の公開版へ前の判断を持ち越さない。文脈判定のバッチごとにも、質問全文・原文・文脈・判定指示・スキーマ・モデル・公開版の完全一致をキーに、正常な判定をCache APIで最大7日保存する。原文再取得後の不変部分や、前回の部分失敗のうち正常なバッチを再利用する。全候補のID・必須フィールド・採用根拠番号を検証し、判断保留や不正な出力は保存しない。キャッシュの再読込でも同じ検証を通す。期限はデータ内でも検査し、エラーや追い出し時は通常の判定へ戻る。モデルが返した実トークン数のみを診断情報に記録し、キャッシュ再利用時に過去の使用量を今回の消費として数えない。無料枠の消費を確認したら、UTC翌日0時まで新規の会議録取得とAI判定を停止する。既に完了している同じ質問のキャッシュは表示できる。停止状態はCache APIで保持し、既知の停止期限を設定した場合も期限後は自動で無効になる。同時に来た同じ質問はキャッシュ照合中も二重判定しない。

8候補の一要求の生成上限は3,072トークン（4候補以下は2,048）とし、24候補で上限合計9,216トークン。上限は消費実績ではなく、推論を含む出力が収まるかの実モデル検証が必要。文脈判定の一要求は60秒でタイムアウトし、公開画面の待機を再試行で際限なく伸ばさない。原文の取得と文脈判定の所要時間を別々に記録する。法令検索は補助資料として非同期表示し、判定結果を待たせない。

公開画面は採用された質疑を最大24件表示する。短い原文抜粋を先に表示し、前後の質問・答弁は展開して読める。判断保留と判定済みの割合を分け、未判定の残り件数も表示する。

## 公開版45：検索語と候補順位の狭い修正

- 「あり方」「在り方」を一般的な問い方として扱い、検索概念の得点に使わない。質問全文と求める変更はAIへそのまま渡す。
- カタカナ語は日本語の単語境界を確認する。「ペット」を「ペットボトル」「カーペット」の一部として数えず、「ペットショップ」や複数語に分割される固有のカタカナ表現は保持する。省庁・政策別の固定辞書は追加しない。
- 第2の対象が複合語なら、既存の第2検索枠でその句を優先する。例は「ペット 生体販売」→「生体販売」。取得要求上限、24候補、判定モデル、意味による採用基準、AI要求の最大3並列は変更しない。
- `test-recall-quality.mjs` は2019年・2026年の衆議院公式会議録抜粋2件と人工的なノイズ40件、既存の代表的な検索語、要求数上限を無課金で検証する。抜粋テストは元の検索結果の再現でも、実際のAI採用件数の保証でもない。



対象語が選択された質問・答弁の引用、原文の文脈、または抽出した受益者・活動領域にない採用候補は、それだけで除外せず、同義語と一般論を区別する追加の意味確認を行います。初回の対象・受益者・活動領域の確認で不採用になった候補は、単語の一致度だけを理由に再判定しません。見落としを再確認する機会は減りますが、全件への二重判定と、追加確認の失敗で不採用が保留へ戻ることを避けます。追加確認は全体で最大8候補に限定し、上限超過や確認失敗は保留します。通常の文脈判定は3要求、対象の追加確認が必要なときは最大5要求です（候補ゼロ時の検索語生成は別）。追加確認は独立した指示・キャッシュキーを使い、同じ候補を確認件数に二重計上しません。

受益者・活動領域・質問対象との関係を別項目で取り出し、上位概念だけの一般論・提供者としての言及・別対象・不明という判定は採用しません。原文の番号と所属の検証は引き続き行います。
