# 初回分析の追加確認待ちを重ねる（2026-10-17）

## 何を変えたか

旧v79では、先行する追加確認は早く開始するが、後続の追加確認は全ての初回判定が完了してから開始していた。
今回は、元の候補順で完了した部分だけで後続の追加確認枠が埋まり、残りの初回判定でその対象が変わらない場合に限り、後続の追加確認を先に開始する。

例として、初回の第1組で追加確認1件、第2組で7件が確定した場合、全体の確認上限8件が埋まる。第3組を待っても追加確認の対象は変わらないので、第2組の確認を第3組の初回判定と重ねられる。第3組の初回判定自体は最後まで待ち、省略しない。

追加確認枠がまだ埋まらない場合や、元の候補順で先にある組が未完了なら従来どおり待つ。到着順だけで優先順位を変えない。予算を超える候補の保留状態も維持する。

## 変えていないもの

最大24候補、初回8件×3組、追加確認全体8件・最大2組、モデル、推論設定、生成上限、全プロンプト、出力スキーマ、原文、各組への割り当て、引用所有元検査、キャッシュ鍵、NDL検索条件は変更しない。
先読みのAI要求・再試行は追加しない。モデルへの入力は追加確認も含めて旧実装と同じで、実行時期だけを変える。結果は従来どおり全ての初回判定と必要な追加確認が終わってから返す。

## オフライン検証

元v79の `semantic-review.mjs`（Git blob `1fbd7485157e7a8ffae3b1ba856178f98bd6a0e9`）をテスト用に保存。実行Workerには含めない。
ローカルNode 22.16.0で、追加確認の対象・予算・完了順を変えた3,750比較、順序に関する3ケース、実際のreviewCompactAssignmentsを使う24ケース、初回判定の失敗9ケース、最後の初回応答を保留する統合テスト1ケース、合計3,787チェックが成功した。

統合テストでは、旧実装と初回・追加確認のモデル要求JSONがバイト単位で同じであること、同じ模擬応答なら採否・原文・引用・順序・件数・保留・エラーが同じであることを検査した。時刻診断だけ比較から除外。模擬モデルの同時実行は最大3のまま。
遅い最後の初回応答を意図的に返さなくても、確認対象が確定した2回目の追加確認が先に開始されることを、実際のレビュー関数で確認した。手順の記録は `initial0, scope1, initial1, scope2, initial2`。

ローカルでは既存npm test全体、Workerビルド、生成Workerの構文確認も成功。AIとネットワークは模擬で、実際の推論呼出は0回。GitHub Actionsの結果は当該PRを参照。

## 限界

これは単一モデルの計算自体を速くする変更ではなく、初回分析中の不要な直列待ちを除く変更。条件を満たさない質問ではこの変更による短縮はない。
本番のモデル待ち・処理時間が同じなら、最後の初回判定と後続の追加確認の重なった区間だけ全体待ちを短くできる。しかし実機の混雑や生成の変動は測定していないため、特定の短縮秒数、常時20〜30秒、意味精度向上は主張しない。
既存の6件未完了の原因を特定・解決した変更でもない。PR #5の出力形式試験とは独立した変更である。
