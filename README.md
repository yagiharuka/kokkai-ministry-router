# 答弁割り振りエージェント

[公開サイトを開く](https://yagiharuka.github.io/kokkai-ministry-router/)

質問案を入力すると、その都度、国会会議録から関連する質問と政府答弁を探します。AIが質問全体の対象・制度・求める措置・範囲を読んで関連性を判断し、実際の答弁者の所属から省庁別の構成比を表示します。政策名ごとの省庁辞書は使いません。

判定モデルはCloudflare上のOpenAI公開モデル **gpt-oss-20b**。Workers AI bindingで稼働します。Qwenや追加料金のかかるサービスへの自動切替は使いません。

## 判定の流れ

1. 質問全文から文法語や一般的な「分野」などを除いて中心の名詞句を抽出し、AIの検索語生成を待たずに国会会議録の発言検索を開始します。検索が薄ければ短い対象語でも追加検索し、候補がゼロのときはAIで自然な言い換えを作って再取得します。
2. 最新100発言の本文を再利用し、発言番号が連続する範囲で質問と答弁を対応づけます。標本が薄い場合だけ、最大10会議を一括で補います。質問と答弁の両方の関連度と会議の分散を使って候補を並べ、別論点への答弁で枠を埋めないようにします。
3. 最大24の質疑・所属の組合せを、最大8候補ずつ3並列で文脈確認します。同じ所属の反復答弁は一度の判定にまとめ、後の答弁も選べます。モデルは候補ID・対象と取組の比較・採否・質問原文番号・答弁原文番号を、項目名付きJSONで返します。引用文・省庁・URL・割合は生成しません。広い政策目的と特定制度への要求を区別し、受益者と提供者の役割を比較します。
4. 対象・制度・求める措置・活動領域・国内外の範囲を文脈で照合し、採用した実答弁の所属から内訳を計算します。複数省庁が答えた一質疑は均等に重みを分けます。根拠は最大24件を表示し、前後の文脈を展開して読めます。
5. 設置法・組織令・組織規則の関連条文は非同期で補助資料として表示します。法令の単語一致だけで担当を決めません。

表示する割合は**取得・確認した質疑の構成比**です。将来の担当になる確率や、正式な所管が確定する確率ではありません。取得件数と検索範囲には上限があります。候補なし・判断保留は、関連する会議録が存在しないことを意味しません。

## 公開構成

- 画面はGitHub Pages。`.github/workflows/pages.yml` が `dist/` を配備します。
- `pages-api/` は会議録取得とAIによる文脈判定を行う中継サーバーです。CloudflareのAI bindingで同じアカウントのWorkers AIを直接呼び出します。
- 国会図書館には検索語を送ります。接続後のCloudflare Workers AIには質問全文と候補の会議録抜粋を送ります。国会図書館のAPIとAI判定は別のサービスです。
- `mcp-worker/` はChatGPTから使う別のMCP接続先です。公開画面と同じ会議録抽出コアを使い、呼び出した会話モデルが文脈を判断します。
- API接続障害や判断保留のときは取得できた候補を残し、未確認の割合は表示しません。AI未接続・無料枠の消費・混雑を区別して表示します。未接続時には検索を始めず、候補0件やNDLの残高不足とは表示しません。有料サービスへの自動切替はありません。
- 同じ質問の正常な完了結果は最大24時間、同じ条件の公開会議録は1時間キャッシュします。保存済みの結果は検索日時を表示します。原文を再取得した後も、質問全文・原文・判定指示・モデル・公開版が完全一致する正常な判定を最大7日再利用します。一部の失敗では、その部分だけ次の検索で判定します。原文や質問が変われば該当部分を新しく判定し、バッチの失敗・不正な原文番号・判断保留は7日保存の対象から外します。キャッシュは追い出される場合があるため、再利用は保証ではありません。

応答時間と候補数は質問や混雑で変わります。最大24候補を3要求で判定し、出力上限は1要求3,072トークン（初回判定の4候補以下は2,048、追加確認は3,072）です。短い配列・分類コードだけの方式では、関連答弁の取りこぼしと項目の混同が実機で見つかったため、項目名と短い比較理由を戻しました。初回AI判定の待ち時間上限は30秒、追加確認は20秒、画面側は115秒です。実際の入力・出力トークン数が返れば診断に記録し、生成上限を実消費量と混同しません。判定の失敗で再試行を増やさず、正常に確認できた他の候補は維持します。日次無料枠の超過が確認された場合は新しい会議録検索・AI要求を止め、日本時間午前9時に停止を解除します。解除後の提供元の残量・応答は別途確認が必要です。

## 開発・検証

```sh
cd pages-api
npm test
npm run build
```

`npm test` は会議録の発言対応、所属、集計、モデル応答の検証と失敗時の表示を確認する無課金のテストです。モデルの意味判断の正答率を測るものではありません。

実際のAPIを使う検証は、Workers Freeの契約とサーバーの接続設定を確認してから手動で行います。無料枠を消費し、モデルエラー時には後続の質問を止めます。有料APIは使用しません。

```sh
node scripts/evaluate-live.mjs
```

検索件数・会議数・抜粋長には上限があり、抽出できない答弁があります。少数の確認例から全体の精度を推定することはできません。

## 初期のPython実装

`server.py`、`router/`、`mcp_server.py` と `scripts/collect_dataset.sh` は、教師データ作成・簡易分類器・ローカルMCPの初期実装です。現在の公開サイトの自動判定には使いません。

教師データを作る例：

```sh
python -m router.ministry_router collect --keyword "半導体" --limit 20 --out data/labeled_pairs.jsonl
```

ローカルMCPはPython 3.10以上で `python -m pip install -r requirements-mcp.txt` を実行し、`python mcp_server.py` で起動します。会話側の手順は `AGENT.md` を参照してください。


対象語が選択された質問・答弁の引用、原文の文脈、または抽出した受益者・活動領域にない採用候補は、それだけで除外せず、同義語と一般論を区別する追加の意味確認を行います。初回の対象・受益者・活動領域の確認で不採用になった候補は、単語の一致度だけを理由に再判定しません。見落としを再確認する機会は減りますが、全件への二重判定と、追加確認の失敗で不採用が保留へ戻ることを避けます。追加確認は全体で最大8候補・2要求に限定し、上限超過や確認失敗は保留します。通常の文脈判定は3要求、対象の追加確認が必要なときは最大5要求です（候補ゼロ時の検索語生成は別）。追加確認は独立した指示・キャッシュキーを使い、同じ候補を確認件数に二重計上しません。

受益者・活動領域・質問対象との関係を別項目で取り出し、上位概念だけの一般論・提供者としての言及・別対象・不明という判定は採用しません。原文の番号と所属の検証は引き続き行います。
